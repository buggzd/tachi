# 实时 SBS 桌面优化报告

日期：2026-09-11。基线：`3be61da`；Android 转换算法仍为 `799661e` 的持有深度与
固定平滑版本。本轮依据[调研报告](../../archive/2026-09-11-realtime-sbs-research.md)
实现独立桌面候选、对照测试及结果记录。**未调用 ADB、未安装或操作手机，也未将
实验候选改为 Android 默认算法。**

结论：最有价值的下一轮候选是 **GPU 降采样读回、按时间常数平滑，以及受限运动传播**。
其中取帧已有明确桌面速度收益；时间平滑需要在响应与噪声之间选参数；运动传播明显
改善移动轮廓，但新显露区域仍有明显错误。保边细化、简化逆投影与直接 CoreML 接入都
没有足够证据支持直接替换现有产品路线。不能把各项孤立耗时相加后宣称手机已经实时。

## 1. 环境、方法与证据范围

- Mac mini：Apple M4、16 GiB 内存，macOS 15.5 ARM64。
- Python 3.11，NumPy 2.4.6，OpenCV contrib 4.11.0（CPU 算法设为单线程），
  ONNX Runtime 1.29.0（模型 CPU 对照设 4 个线程）。
- Chrome 152.0.7977.83，headless WebGL2，实测 renderer 为
  `ANGLE Metal Renderer: Apple M4`，不是软件 SwiftShader。
- 深度模型：既有固定输入浮点 Depth Anything V2 Small，266×154；SHA-256：
  `3a4faf23bffbdfed714116c0a2c375bdac9d69401af4f21953468e8ac5793b7b`。
  **不是 Android 的 U16/I8 量化图**，CoreML 与 CPU 比较使用同一个浮点文件。
- 复用三段本地匿名 Jellyfin 摘录，不访问账号、不写播放进度。浏览器每片段每模式
  8 秒计时，另有 1 秒预热，模式顺序交错；不是多轮长时间热稳态实验。
- 合成真值覆盖静态噪声、局部深度阶跃、匀速前景平移、遮挡/显露、明显切镜。
  绘制覆盖平滑深度、遮挡阶跃和薄线。真实片源没有几何真值，光流/深度对应误差
  只能作诊断，不能替代真实深度误差或眼镜舒适度。
- 深度误差统一乘 30，表示**源图坐标下单眼视差像素**；不包含虚拟银幕缩放。
  合成时间滤波保留浮点内部状态，未加入最终 U8 舍入，其单眼误差上限约 0.059 px。

复现步骤与固定依赖见 [experiments](../../../StereoLab/experiments/README.md)。
[算法数据](algorithms.json)、[真实深度诊断](real-depth.json)、[取帧数据](capture.json)、
[绘制数据](warp.json)、[CoreML 数据](coreml.json) 为机器可读的统计结果，非逐帧原始轨迹。
所有计时均为本机结果；没有 Android WebView/JNI/QNN、眼镜输出、音画同步或功耗测量。

## 2. 取帧：收益最明确，但异步并不意味着更低帧龄

比较同一 HTML video 的三条路径，均输出 266×154 RGBA：

1. CPU Canvas `drawImage + getImageData`。
2. WebGL 纹理上传、GPU 降采样、同步 `readPixels`。
3. 同样 GPU 降采样，两个 PBO + fence；后续 rAF 以零超时检查完成状态，完成后
   `getBufferSubData`。不会提交后立即阻塞等 fence；满槽丢采集，不排无限队列。

| 片段 | CPU Canvas 平均 / P95 ms | WebGL 同步平均 / P95 ms | PBO 提交＋取回平均 / P95 ms | PBO 结果帧龄平均 ms |
| --- | ---: | ---: | ---: | ---: |
| 0 | 9.12 / 12.40 | 3.31 / 4.20 | 0.78 / 1.10 | 17.05 |
| 1 | 8.84 / 12.80 | 3.30 / 4.30 | 0.76 / 1.20 | 17.04 |
| 2 | 7.84 / 10.80 | 2.57 / 3.70 | 0.65 / 1.00 | 17.07 |

三段均值由约 8.60 ms 降为同步 3.06 ms（约 **64%**），或异步调用工作 0.73 ms
（约 **92%**）。后一个数不包含两次调用之间的等待，也不包含 fence 轮询与其他
浏览器工作的完整线程 CPU 占用；不能写成“完整取帧延迟 0.73 ms”。

有效完成率约 23.87–25.00 fps，符合片源约 24/25 fps；无容量丢弃、视频解码掉帧或
GL 错误。预热期计入视频质量计数，但不计入阶段计时。两个 PBO 共 **327712 B**，
这个上界不包含解码纹理、上传纹理及浏览器其他内存。

在同一暂停视频帧上验证同步与 PBO 实际读回的颜色/行方向，RGBA 平均误差低于
0.022/255。验证发生在计时窗口外，避免同时 CPU 读回污染候选计时。

**决策：保留同步 WebGL 和 PBO 两个候选。** PBO 降低阻塞，但本实现轮询让帧龄
增至约 17 ms；单线程有空余时同步方案可能更低延迟。下一阶段必须加入真实帧桥、
QNN 与双眼绘制共同测量，尤其检查 Android WebView 的视频上传路径是否也有收益。
本轮没有端到端流水线排程/并发基准，也没有声称零拷贝。

## 3. 时间平滑：固定系数确实存在低帧率迟滞

保持现有外观/深度差门控，只将范围与像素更新改为
`alpha = 1 - exp(-deltaTime / tau)`，对照 80/160/320 ms。
静态测试加入独立像素噪声及整体尺度/偏置扰动；真值不变。阶跃响应另用无噪声序列，
避免噪声提前越过 90% 阈值造成虚假“响应很快”。

8 Hz 结果：

| 方法 | 稳定区域绝对视差误差 P95 px | 小深度阶跃首次持续到 90% 的时间 ms |
| --- | ---: | ---: |
| 原固定 0.15 / 0.35 | 0.390 | 625 |
| 时间常数 80 ms | 0.565 | 125 |
| 时间常数 160 ms | 0.477 | 250 |
| 时间常数 320 ms | 0.348 | 625 |

“持续”要求三个采样均越过阈值。时间从**首张阶跃深度到达滤波器**计，不含采集、
推理与传输；离散采样误差最多约一周期。小阶跃幅度为原始相对深度 0.04。
固定系数在 4/8/16 Hz 下分别需要 1250/625/312.5 ms；160 ms 时间常数对应
250/250/312.5 ms，明显减少随更新频率变化的迟滞。

较大阶跃 0.09 在本构造中越过现有 0.12 归一化差门槛，所有方法直接采用首张新图，
因此测得 0 ms。这不是零播放延迟，而是**门控响应不连续**的证据。

真实片源每三帧做一次实际模型推理，每段 32 张观察。对可信光流对应点计算视差变化
P95（包含真实运动，越低不必然越好）：

| 片段 | 原始逐帧归一化 | 固定系数 | 160 ms | 320 ms |
| --- | ---: | ---: | ---: | ---: |
| 0 | 9.255 | 10.812 | 8.599 | 9.339 |
| 1 | 3.274 | 3.969 | 3.603 | 3.738 |
| 2 | 1.032 | 0.612 | 0.677 | 0.572 |

**决策：160 ms 作为响应优先候选，320 ms 保留作稳定优先对照；不宣布通用最优值。**
160 ms 在本 8 Hz 合成测试低于探索门槛 0.5 px，但 4 Hz 为 0.550 px，真实片段 2
也比固定系数的对应变化略大。320 ms 不能靠更慢响应“赢得”全部评价。下一步需把
硬门控改为连续置信权重，并结合运动对齐，不能只替换一个 alpha 就声称抖动解决。

## 4. 运动传播：轮廓改善明显，新显露区域仍是短板

266×154 DIS ultrafast 双向流，以前后向一致性、光度残差和坐标有效性计算可信度。
模拟 24 Hz 显示、8/12 Hz 理想深度观测，观测固定延后两个显示帧到达。迟到结果
通过捕获帧到当前帧的每一段历史流传播，不把“warp 一次”当作已追上当前画面。
低可信度处保持已有非零深度，没有整幅回退平面。

8 Hz 深度、24 Hz 显示的合成匀速平移：

| 方法 | 全图视差 MAE px | 轮廓带视差 MAE px | 新显露区域视差 MAE px |
| --- | ---: | ---: | ---: |
| 直接保持旧图 | 0.427 | 5.152 | 18.000 |
| DIS 无可信度过滤 | 0.058 | 1.018 | 4.779 |
| DIS 有可信度过滤 | 0.110 | 1.910 | 11.891 |

带可信度方案轮廓误差下降约 **63%**；双向 DIS 平均约 1.56 ms，传播约 0.24 ms。
12 Hz 带可信度方案轮廓误差约 1.66 px，新显露区域仍约 10.57 px。

无过滤在这个简单有纹理场景更好，不代表复杂视频也应该去掉可信度保护。带可信度
版本在新显露区域拒绝旧映射后持有错误旧值，是其误差仍高的直接原因。当前实验没有
可靠的背景补全/可见性模型；不能宣称已经修复遮挡。

三段真实视频各 95 对相邻帧，双向流平均约 1.4 ms，可信区域占比分别约
89.5% / 91.4% / 96.9%。可信区域光度 MAE 从 2.05 / 1.76 / 1.64 降到
1.10 / 0.65 / 1.09（0–255 灰度）。该指标衡量图像对应，不衡量深度真值。
没有与现有 JS block matcher 直接 A/B，也未计每视频帧获取运动缩略图的代价。

明显切镜的独立测试中，收到新场景观察后可立即重置范围历史，残余为零；在理想
两帧延迟下，新图到来前仍持有旧场景约 83 ms。相似颜色切镜未覆盖。

**决策：继续保留运动传播候选，但先修正新显露区域再考虑产品启用。** 帧历史必须
有界、观测必须带媒体时间；不能为运动额外加入一条昂贵的完整视频 CPU 读回路径。

## 5. 尺度注册、保边与绘制消融

### 鲁棒尺度注册

12000 个合成对应点、20% 错配，单次仿射拟合中，普通最小二乘视差 MAE 为
1.052 px，五轮有界 Huber 拟合为 0.039 px。该项只有单次调用计时，不能当作稳定
性能基准；它也尚未接入上述时域管线。

这仅说明鲁棒残差对错误对应有用。全局真实前后运动也可能表现为尺度变化，当前
拟合没有证明能区分真实运动与模型漂移，**暂不强制注册到历史深度**。

### 半分辨率保边细化

266×154 深度到 960×540，包含曲线边界与 RGB 纹理的合成场景；预热 3 次、测量 10 次：

| 方法 | CPU 平均 ms | 单眼视差 MAE px | 边界 F1（2 px 容差） |
| --- | ---: | ---: | ---: |
| 双线性 | 约 0.16 | 0.0302 | 1.000 |
| Guided filter | 约 4.23 | 0.0332 | 1.000 |
| 双线性后 joint bilateral 细化 | 约 20.35 | 0.0265 | 0.619 |

联合双边在这里是 OpenCV 全分辨率细化，**不是原论文从低网格直接求解的完整 JBU
复现**。Guided 没有提高本场景边界指标；双边虽然降低全图 MAE，却增加边界检测的
破损/多边响应。远离边缘的纹理泄漏接近零，不证明所有纹理/头发场景都无泄漏。

**决策：不把这两个 CPU 版本搬进产品。** 后续可研究低分辨率系数的 fast guided
或 GPU 实现，并增加模型漏检细线、纹理与几何边界不一致的真值测试。

### 双眼绘制

在桌面 WebGL 中翻译现有 gather 思路，静态颜色纹理与低分辨率深度输入，每眼
1920×1080，预热 3 次、测量 12 次，以 GPU timer query 计时：

| 场景 | 33 候选 GPU 平均 ms | 2 次逆投影 ms | 4 次迭代＋局部搜索 ms |
| --- | ---: | ---: | ---: |
| 平滑 | 2.44 | 0.82 | 0.73 |
| 遮挡阶跃 | 3.71 | 0.45 | 0.96 |
| 薄线 | 2.54 | 0.64 | 2.43 |

纯逆投影在薄线场景有约 **22.7%** 像素与 gather 相差超过 RGB 三通道绝对差总和 12。
混合版本在薄线场景退回搜索，与基线一致，但速度收益几乎消失；在平滑/遮挡场景仍
分别有约 3.8% / 4.5% 像素差异。UI 与 letterbox 区域均保持基线像素不变。

输出差异不全等于画质下降：整数候选与连续逆投影本来就有亚像素差异。但没有新视角
真值，不能凭速度或 MAE 证明可见性正确。稀疏梯度检测也不是全区间收敛保证。
**不直接替换 Android AGSL**；需补充可见性、边界覆盖与实际 WebView 纹理测试。

## 6. M4 Neural Engine 路线

ORT CoreML 选择 `MLComputeUnits=CPUAndNeuralEngine`、静态输入与 MLProgram，
因此没有选择 GPU；但这个设置允许 CoreML 内部用 CPU，不能证明全部由 ANE 执行。
同一浮点模型、6 张已有校准图、预热 3 次后 18 次推理，双方均开启 ORT profiling：

| 后端 | 建会话 ms | run 平均 / P95 ms | 分配证据 |
| --- | ---: | ---: | --- |
| CPU，4 线程 | 168 | 25.82 / 32.24 | CPU EP |
| CoreML CPU＋ANE | 18924 | 33.92 / 45.38 | 每次 25 个 CoreML 分区事件＋48 个 CPU 节点事件 |

CoreML 支持日志显示图中 650 节点有 602 可分配给 CoreML。结果与 CPU 输出的
P5–P95 范围归一化 MAE 平均约 `2.52e-6`，但速度更慢。预处理已在计时前完成；
profile 也有开销，不能把这组 run 时间称为无分析器的生产性能。

**决策：本轮不继续投入直接 ORT→CoreML 路线，不将 M4 当作骁龙 NPU 模拟器。**
后续若专门优化 Apple，需要减少分区、验证原生 CoreML 导出，并用 Apple 工具核验
硬件放置。Apple 浮点/ANE 与 Qualcomm QNN U16/I8 的算子、内存和调度差异，不能
通过一次 Mac 跑分消除。

## 7. 下一阶段建议与验证状态

| 候选 | 桌面结论 | 下一步 |
| --- | --- | --- |
| WebGL 降采样＋同步/PBO 读回 | 速度收益明确，颜色/行方向验证通过 | 优先进入后续手机 A/B，计入桥、QNN、渲染与帧龄 |
| 按时间平滑 160/320 ms | 响应可控，稳定与跟随有取舍 | 保留可切换参数，继续替代硬阈值；不能宣布消除抖动 |
| 可信 DIS＋有界历史 | 运动轮廓改善，显露区域错误仍大 | 先补桌面显露/低纹理/切镜反例，再考虑启用 |
| 鲁棒全局注册 | 对错配有效，真实纵深运动未解决 | 暂不加入默认时序管线 |
| CPU 保边细化 | 本构造收益不足或边界变差 | 暂不采用 |
| 逆投影/混合绘制 | 速度更快，但可见性证据不足 | 暂不替换 AGSL |
| ORT CoreML CPU＋ANE | 分区多且更慢 | 不用于模拟手机 NPU |

四项算法回归（保持旧深度、恒等流、时间常数跨频率一致、切镜历史重置）通过；
浏览器捕获颜色/方向、GL 错误、PBO 容量及绘制保护区检查通过。报告保留负结果，
未因候选更快而降低“一个 WebView/video、无慢帧平面回退”的约束。

本轮未覆盖 VDA/FlashDepth/动漫大模型替换、真机 QNN 并发、实际 NPU/GPU 缓冲共享、
完整融合管线、整集热态和光学体验。**已有足够桌面证据选择下一轮测试对象，但没有
足够证据宣布完整实时 SBS 性能或画质验收通过。**
