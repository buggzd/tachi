# 2026-09-12 MyGO 失败链与画质回传

输入为用户第二份 `format=4 / nativePlaybackSchema=2`、0.3.1-debug 报告；此前交付基线 `8cee14f`。
本轮没有连接手机或运行 ADB。报告包含 94 个样本、36 条阶段事件和 4 条失败记录。
不保存原始附件、媒体 ID、账号、服务器地址或认证 URL。

## 已定位的播放问题

用户所述 MyGO 第三集对应两次 1419.97 秒片源尝试：

| 次序 | 位置 | 状态 |
| --- | ---: | --- |
| attempt 1 | 0.361 s | 已出首帧，`c2.qti.hevc.decoder`，随后 Media3 `2000` |
| attempt 2 | 0.359 s | 同样已出首帧，随后 Media3 `2000` |

两次均为 HEVC/MKV、AAC 44.1 kHz、ASS，深度 `disabled`、计算次数 0。
Media3 1.5.1 将 2000 定义为 `ERROR_CODE_IO_UNSPECIFIED`；报告的 HTTP 0 表示未提取到 HTTP 错误状态，
不是 HTTP 成功证明。此错误不等同于硬件解码器不支持，更不可能由当时尚未运行的深度推理引起。

每次错误之后都有 `fallback → stopped → command_rejected`，没有新的 HLS open。
使用本地凭据从实际 Jellyfin 获取该集播放计划，复现直放地址使用 `/Videos/`、HLS 地址使用 `/videos/`。
原生校验原先只接受大写路径，因此拒绝合法回退。修复只对 Videos API 段做大小写兼容，
同 origin、反向代理子路径大小写、路径边界和遍历防护保持；添加针对性 JVM 用例。
被拒绝的当前代次 open 现在向对应播放器返回固定错误，避免无限 buffering；旧账号/无效 token 不回传。

实际 HLS master 和 variant 均 HTTP 200，含分段；声明 H.264/AAC、1920×1080、23.976 fps。
测试结束后删除本次转码会话（HTTP 204），未更改用户播放进度。桌面端点检查不代替实机 HLS 解码验收。

另外发现 Media3 默认会在解复用时提前解析嵌入字幕，即使文字轨道未选中。tachi 字幕归 libass/WebVTT 所有，
因此显式使用不支持任何格式的原生 SubtitleParser.Factory，停止重复原生字幕解析；前端 ASS 不变。
实际文件首批复杂 ASS 数据在 0.480 秒附近，接近失败位置，但当前日志没有异常原因链，
尚不能断定 ASS 解析就是原始 2000 的根因。新增 errorKind/errorComponent 固定分类用于下一次复现，
不输出异常消息、类名、栈、URL 或字幕文本。

## 鬼影 / 抖动的证据

第三次成功播放为另一段 2924.244 秒媒体。取 62 条 playing 且 depth ready 的样本：

- 首尾跨度 61.906 秒，深度吞吐 12.002 Hz，解码吞吐 23.972 fps，解码丢帧 0。
- 导出时刻深度帧龄最小 37 ms、中位 94.5 ms、经验 P95 137 ms、最大 149 ms。
- 暂停后 stopped 的 943 ms 帧龄不参与上述统计；暂停会正常延长有效深度的年龄。
- 最后一条 playing 窗口：推理 18.084 / P95 19.108 ms，CPU 稳定 17.826 / 22.311 ms，
  采集到上传 57.316 / 66.310 ms，GPU 7.643 / 7.750 ms。

帧龄是采样到观察时刻的墙钟年龄，不是视频 PTS 差，也不是精确显示延迟。代码仅携带采集时刻到输出，
没有按视频 PTS 配对；当前纹理使用最近收到的深度。结合这些数据，可确认存在时间对齐缺口，
但用户未提供图像序列，无法对可见伪影进行逐像素归因。

其他源码事实：TemporalDepth 在相同像素坐标融合历史，没有运动重投影；每帧百分位归一化；
运动门限和深度差门限是硬切换；266×154 的深度以普通线性过滤放大；双眼 gather 遇到没有有效
反投影解的区域会选择误差最小的候选，缺少显式遮挡露出区域与可靠填洞。以上均可能导致边缘拖尾、
轮廓爬动或拉伸，不应把“解码丢帧 0”当成时序画质通过。

参见 [DLSS / FSR 公开资料与 SBS 改造建议](../../archive/2026-09-12-dlss-fsr-sbs.md)。
本轮修复播放回退与字幕所有权、补充错误分类；未宣称实现光流、PTS 帧队列或消除画质伪影。
