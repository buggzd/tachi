# 捕获与液化排队顺序：端到端短测

## 结论与采用范围

采用 **补采后立即提交液化** 的 v2，纳入 `build-sbs-experiment.sh liquid`；Gradle `captureBeforeLiquid` 通用默认仍为 false，普通 Full 与旧档位不变。独立轮询线程仍关闭。保持 392×224、P2/P98、严格同帧双槽、0.85／96 px／65%、FP32 和八次扩散，不改变像素偏移回归路径。

同片源顺序短测从 22.68 到 23.62 新配对 Hz（+4.13%）；捕获到配对绘制开始从 85.80 到 82.06 ms；软件视频减配对 PTS 均值从 92.49 到 81.94 ms。尚非稳定 24 Hz，也不是测得的物理屏幕延迟改善。顺序测试非随机、非热态控制，NPU 时长也有约 1% 波动，收益不能全部作严格因果归因或外推到所有片源。

## 实现与第一性原理

旧顺序在 `processGpuDepth` 中复制对应深度并立即提交液化，之后才释放捕获槽、尝试补采。下一次捕获 fence 因而可能排在上一帧液化后面。

v2 接受匹配 RGB/depth 后释放槽，在现有 GL 线程尝试补采，随后立即提交液化；`onDrawFrame` 中也在捕获之后、绘制之前提交尚未计算的当前配对。场计算按配对序号只提交一次，旧代配对不提交。

成功补采时，输入 fence 先于液化入队，使输入完成与后续计算有重叠机会。新解码帧已 pending、采样不需要或槽仍忙时不强行捕获；仍严格沿用原 admission。没有新队列、额外槽或旧深度配新 RGB。对应完整 RGB 纹理交换、深度独立快照、同一 GL 队列的顺序及 barrier 保证对应关系；渲染前必须计算该配对的位移场。

双槽有近似吞吐约束：平均占槽 85 ms 时，满占用理想上限约 2/0.085=23.5 Hz；24 Hz 需约 83.3 ms 以下。这里是分析模型，`captureToUpload` 不是精确 lease 生命周期，不能将该估算当实测上限。

## 为什么没有采用第一版

v1 将液化完全推迟到下一次绘制。捕获到上传降至 79.56 ms，但捕获到绘制开始为 86.46 ms，未优于基线。新增下游指标揭示了等待转移，故没有只凭上传指标采纳。

v2 在补采之后立即提交液化，不额外等待绘制回调；只有 `onDrawFrame` 自己处理新配对时才在其捕获之后提交。保留此实现，v1 仅留测量证据。

## 验证与限制

- 142 app + 25 native-video JVM 测试、lint、APK 资源/内容校验通过；新增指标有白名单边界测试。
- 连续播放、暂停、暂停中 +10 秒 seek、恢复播放、再次暂停通过软件状态采样；seek 后配对 PTS 跟随新位置，恢复后无 PTS 缺失/未来深度上报。见 [恢复数据](recovery-summary.json)。这不证明所有过渡帧、后台、Surface 重建与插拔均已验收。
- 每轮约 100 秒 SurfaceFlinger 子窗口：实际采样最大间隔 <1.74 秒，present 间隔 P95 约 16.60 ms、最大约 49.80 ms；含缓存重复，非转换 fps。
- 电池采样约 27.2–31.0°C，充电且顺序运行，thermalStatus 样本均 0；不能推断没有频率变化或续航改善。
- 沿用已知冷启动目录 UI 放大裁切问题，原生视频画幅正常；未在本轮修复，不宣布完整 UI/字幕显示及独立音画同步通过。
- 已暂停播放，保留 v2 供用户观影；后续长时间温控、画质与同步由用户反馈，工程矩阵仍需后续完成。
