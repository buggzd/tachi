# 官方 QAIRT 的 SM8850 实机验证

日期：2026-09-10。独立测试 APK，不改变正式播放器。

## 运行环境与证据边界

- Xiaomi 2509FPN0BC，SM8850 / Hexagon V81，Android 16 / API 36。
- 官方 QPM 下载、解包 QAIRT 2.50.40.260831；QIK SHA-256：
  `0a0a66f540fdca697c5d041174576e5a5d989153fb78dafdae0658cd078eccfd`。
- 同 SDK 的 QNN API 2.39 头文件、ARM64 backend/Prepare/V81 stub/Calculator、
  V81 unsigned DSP 库打包进独立 APK；FastRPC 使用 Android 提供的库。
- Direct QNN：backend/device/context/graphCreate/finalize/execute 全部成功，
  U8 Relu 输出逐项匹配参考值。unsigned PD 在本机可用。
- ONNX Runtime Android QNN 1.22.0；禁用 CPU fallback，
  `offload_graph_io_quantization=0`。Smoke 与深度 profile 均只有
  `QNNExecutionProvider` 执行事件。

这解决了旧 vendor-copy 实验的运行库不完整/API 不匹配问题。设备创建或库加载
本身不作为成功依据，必须运行图并核验结果。

## 深度模型

输入 `1×3×154×266`，Depth Anything V2 Small，U16 激活 / I8 逐通道权重。
模型 SHA-256 与汇总数据见 [机器可读证据](qairt-device.json)。U16/U8 候选因逐通道卷积权重
必须为 signed 类型被严格 QNN 拒绝，未启用 CPU 回退绕过。

| 测试 | 次数（另有 5 次热身） | 平均 | P50 | P95 |
| --- | ---: | ---: | ---: | ---: |
| 初测：run + 输出读取 | 30 | 23.469 ms | 23.482 ms | 25.869 ms |
| 初测：张量创建 + run + 输出读取 | 30 | 23.738 ms | 23.674 ms | 26.056 ms |
| 连续：run + 输出读取 | 3000 | 22.678 ms | 23.165 ms | 23.841 ms |
| 连续：张量创建 + run + 输出读取 | 3000 | 22.960 ms | 23.472 ms | 24.213 ms |

连续测试约 70 秒；会话初始化约 2.47 秒，单独计量。输入为预处理好的真实
Jellyfin 校准帧轮换，不含视频取帧、缩放、归一化、WebView bridge、时间传播、
SBS 渲染或等待显示。约 43.6 次/秒是这个测量范围的吞吐量，不是播放器帧率。

最后一次实际输入与输出在计时后保存，以同一输入运行桌面 CPU 模型：
相对相同量化模型，归一化 MAE 0.00678、Spearman 0.99985、排序一致率 99.51%；
原始 MAE 0.08956，存在尺度/偏移差异，不能称为逐值一致。
相对浮点模型，归一化 MAE 0.0424、Spearman 0.9861。
这只核验一个校准帧的运行结果，尚未覆盖独立测试集和视频时序质量。

## 实时预算

24/25 fps 的每帧预算为 41.67/40 ms。连续深度测量的 P95 24.21 ms，
独立 Full SBS 3840×1080 合成的同步等待 P95 为 7.3–7.9 ms，二者单独测量
均低于帧预算。但不能直接把两个 P95 相加作为联合 P95，也不能据此宣称完整
播放器已经通过。需要验证并发争用和剩余的数据路径。

## 并发验证

证据：[时间窗口与执行分区](qairt-concurrent.json)。独立测试 APK 在本地处理
模型输入期间启用临时前台服务，避免切换 Chrome 后 Android 冻结缓存进程。
确认 `QNN_DEPTHSessionInitMs` 后才切换 Chrome；服务在测试完成后自动停止，
实机 `dumpsys activity services` 已确认没有遗留服务。

| 项目 | 结果 |
| --- | --- |
| NPU 连续执行 | 6000 次测量 + 5 次热身，约 150.6 秒；6005 个事件全部为 QNN |
| run + 输出读取 | 平均 24.695 ms，P50 24.189 ms，P95 29.413 ms |
| 张量创建 + run + 输出读取 | 平均 25.046 ms，P50 24.528 ms，P95 30.032 ms |
| SBS 三个片段，各 20 秒 | 23.844 / 23.893 / 24.946 fps，片源 23.976 / 23.976 / 25 fps |
| 每眼 1920×1080 合成与同步等待 P95 | 4.1 / 6.0 / 6.8 ms；每帧 `gl.finish()` |
| 解码丢帧 / GL 错误 / 隐藏帧 | 均为 0 |

浏览器记录测量起止 epoch 时间，ORT profile 用手机本地时间的文件名对齐。
文件名只有秒精度，因此每个 20 秒窗口两端各去除 1 秒后核验：
758 / 680 / 661 次 NPU 图执行；窗口内图耗时 P95 为 27.269 / 29.658 / 30.652 ms，
相邻图启动的最大间隔约 43.3–43.8 ms。NPU 运行覆盖全部三个窗口并留有时钟误差
余量，没有后台暂停。6000 次整体统计还包含 SBS 窗口外的运行，不应称作纯并发
区间统计；窗口内图耗时不包含 Java 张量构造与输出读取。

SBS 使用动画合成深度，NPU 独立轮换预处理好的真实帧，两者没有传递深度。
这证明并发算力余量，不是端到端 SBS 视频通过。回调间隔 P95 约 67–68 ms，
吞吐达标也不代表每一帧都准时呈现；尚未进行长期热态验收。

第一次尝试因无线 ADB 断开中断；后续仅打开两个 Activity 的尝试也被排除，
因为前台切换过早或 Android 冻结后台进程，不能计为并发证据。最终仅采用有
前台服务且 profile 时间窗口验证通过的一轮。独立 3000 次 profile 也已完整
取回并核验 3005 个 QNN 事件。

## 结论与后续验收

原路线的两个计算环节在本机满足 24/25 fps 的吞吐预算，并已验证能够并发。
正式播放器的实时 SBS 尚未完成以下验收：

1. 将实际 NPU 深度送入合成器，测视频取帧、预处理、深度上传、帧龄与同步；
   确认加入这些成本后仍满足预算，决定逐帧深度或低频深度加时间传播。
2. 独立片段检查深度量化误差、遮挡补洞、快速运动、场景切换与时间传播。
3. 应用 WebView、眼镜输出、字幕/音画同步及更长热态播放回归。

构建与验证：独立 APK `assembleDebug`、`lintDebug` 成功；主机 U8 Relu
参考向量验证通过；上述实机 Direct、strict smoke/depth 和并发证据通过。
正式播放器代码未更改，未把这些结果外推为正式播放器回归通过。
