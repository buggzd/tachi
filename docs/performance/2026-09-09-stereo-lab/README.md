# 2026-09-09：实时深度 SBS 桌面功能验证

## 结论与范围

独立 `StereoLab` 完成了在线深度估计、双眼重投影、遮挡/补洞、时间传播以及
Debug 深度图显示的桌面功能验证。三个真实 Jellyfin 片段均在每眼 1920×1080
输出下跟上各自约 24/25fps 的播放，未观察到视频解码丢帧或视频回调遗漏。

这不是手机或 Android APK 的通过结论。输入是从 Jellyfin 提取并在电脑转为
H.264/AAC 的本地片段；测量不包含 Jellyfin 网络播放、HLS、原生 NPU、USB 眼镜、
光学舒适度或端到端音画同步。本轮也不证明电影全长运行、功耗、温升或深度准确率。

## 环境与复现

- 主机：Apple M4，macOS arm64；Chrome 152.0.7977.82，WebGPU + ANGLE Metal。
- 基线：`2ec600c` 上的本次实验实现；原始 JSON 的 `provenance` 保存实际测量时
  核心文件 SHA-256 和模型 revision，可与后续改动区分。
- 模型：Depth Anything V2 Small，FP16 ONNX；模型 I/O 输出实测为 float32。
  固定权重、许可证和下载方式见 [实验指南](../../../StereoLab/README.md)。
- 片段：三个不同媒体的 20 秒、1920×1080 本地样本，包含绘制风格画面和室内人物场景；内容类型覆盖有限。
  源帧率分别为 24000/1001、24000/1001、25fps。未提交真实片段、截图、媒体标题或 ID。
- 输出：3840×1080 Full-SBS，内容大小 90%，基础视差 8px，立体幅度 24px。
- Debug：原视频、模型深度图、时间对齐深度图全部开启；渲染工作深度网格为 96×54。

```bash
npm --prefix StereoLab ci
npm --prefix StereoLab run models
npm --prefix StereoLab run samples
npm --prefix StereoLab test
npm --prefix StereoLab run build
npm --prefix StereoLab run verify -- --seconds 60 --width 1920 --input 266
npm --prefix StereoLab run verify -- --seconds 12 --width 1920 --input 518
```

每个片段先完成模型预热再计时。60 秒测试会覆盖多次自动循环；短循环的媒体重启
占用少量墙钟时间，因此平均提交率略低于标称帧率。解码计数与回调计数独立采样，
边界上可能相差一帧。只有一个推理请求在途，数据过期会降低立体强度。

## 测量结果

266×154 输入，每段 60 秒；[原始技术数据](input-266.json)：

| 样本 | SBS 提交 fps | 深度处理均值 ms | SBS GPU 均值 ms | 深度年龄 P95 ms | 有效立体帧占比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 23.83 | 31.99 | 7.96 | 83.42 | 99.09% |
| 2 | 23.87 | 31.62 | 8.11 | 83.42 | 97.70% |
| 3 | 24.91 | 31.99 | 8.40 | 80.00 | 97.12% |

518×294 输入，每段 12 秒；[原始技术数据](input-518.json)：

| 样本 | SBS 提交 fps | 深度处理均值 ms | SBS GPU 均值 ms | 深度年龄 P95 ms | 有效立体帧占比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 23.91 | 63.99 | 5.46 | 208.54 | 97.56% |
| 2 | 23.98 | 63.87 | 5.50 | 208.54 | 95.83% |
| 3 | 24.99 | 64.62 | 5.58 | 200.00 | 93.00% |

较大输入仍能维持视频驱动的 SBS 提交，但深度更新约为 9Hz，必须依赖中间帧运动
传播；更高的深度年龄会增加快速运动时的错位风险。这支持默认从 266px 性能档开始，
不支持宣称 518px 能为每个视频帧生成独立的新深度。

两档分时运行且采样时长不同，不能把 GPU 时间差解释为大输入使合成更快。
`inferenceMs` 包含预处理、推理、同步和结果读取，`gpuMs` 来自 GPU timer query；
两者不能简单相加当作逐帧串行耗时。提交 fps 也不是眼镜物理呈现 fps。

实际素材和 Debug 截图保存在各工作区被忽略的 `StereoLab/.local/verification-*`

## 手机 Chrome 初测

Android 16 / API 36，SoC SM8850，Chrome 150，通过无线 ADB reverse
读取同样的三个本地 Jellyfin 片段。Debug 开启，WebGPU FP16，实际模型
输入 266×154，每眼 640×360；每片段预热后测量 12 秒。
[匿名原始指标](android-640-266.json)记录功能通过、实时性能未通过。

| 片段 | SBS 回调 fps | 推理平均 ms | 有效立体帧 | 深度年龄 P95 ms |
|---|---:|---:|---:|---:|
| 1 | 17.02 | 59.25 | 94.76% | 291.96 |
| 2 | 19.51 | 60.34 | 97.89% | 250.25 |
| 3 | 19.25 | 58.55 | 92.80% | 240.00 |

几何、真实模型深度变化、非平面双眼差异、Debug 深度、暂停、seek 和单视频
断言全部通过，解码丢帧为零，但输出回调低于源帧率的 90%。
GPU timer 不可用，不能将主线程耗时当作 GPU 时长；当前数据不足以区分
纹理读取、同步等待和运动估计的具体贡献。无线传输、调试及短测影响仍未排除。
未验证 APK WebView、NPU、眼镜呈现、音画同步或热稳定性。
首轮请求 266 但测得 518 的记录不作为受控基线；验证器现强制选择并校验输入档位。

## 手机 P0/P1 分项测试

完整脱敏数据见 [android-p0-p1.json](android-p0-p1.json)。测试期间设备接 USB 电源，
电池约 37°C，系统 thermal status 为 0；这些是采样时刻，不是长时间热态结论。

60 秒基线在 266×154、每眼 640×360 下得到 17.49–19.23 fps，推理均值 63.95–65.01 ms，
有效立体帧占比 93.33–96.40%。三个片段均没有视频解码丢帧，但没有达到实时门槛。

阶段计时显示，取帧并读取/转换 96×54 缩略图约 10–19 ms，送入模型前按 266 档再次缩放、
读取和 RGB 打包约 8.4–10.3 ms；两者合计是主要主线程阶段。运动估计约 2.4–3.6 ms；
Debug 画布约 0.33 ms；WebGL 提交约 0.74–0.93 ms。关闭 Debug 的短测没有
稳定改变输出帧率，强制 `gl.finish()` 也没有明显增加合成等待；手机不支持
`EXT_disjoint_timer_query_webgl2`，所以 GPU 时间仍未知。

关闭渲染后输出约 18.67–20.96 fps，关闭运动传播并关闭渲染后约 20.24–21.54 fps，
说明运动估计有可见但有限的成本。无运动模式只用于开销隔离，不能作为画质结果。
将推理间隔限制为 100 ms 后，输出约 16.47–18.66 fps，深度年龄上升，简单降频没有解决问题。

输入档位对手机影响明显：

| 深度输入 | 推理均值 | SBS 回调 fps | 有效立体帧占比 | 结论 |
|---|---:|---:|---:|---|
| 266×154 | 约 59–65 ms | 约 17–21 fps | 约 93–98% | 当前性能档，仍未实时 |
| 378×210 | 约 101–109 ms | 约 15.6–16.4 fps | 约 87–93% | 细节增加但更过期 |
| 518×294 | 约 202–206 ms | 约 12.9–13.2 fps | 约 38–44% | 不适合实时转换，并出现少量解码丢帧 |

每眼输出从 640 提高到 1280/1920 没有使主线程计时显著增加；这不能证明 GPU 合成
没有成本，因为浏览器没有 GPU timer。当前优化优先级应放在视频像素读回/转换和深度推理，
而不是 Debug 或 SBS 几何。

## APK WebView 能力探测

在已安装的 debug APK 中只读检查了 Companion 和 Glasses 两个 WebView。系统 WebView
150.0.7871.181 能申请 WebGPU adapter/device，并报告 `shader-f16`、`timestamp-query`；
同时具备 WebGL2、Worker、OffscreenCanvas 和 H.264/AAC MP4 解码能力。WebGL timer query
仍不可用。StereoLab 尚未打包进 APK，因此这只是运行时能力证据，不是 WebView 端到端
深度推理或 SBS 通过结论；完整数据见 [android-p0-p1.json](android-p0-p1.json)。

## 2026-09-10 SBS 合成独立验证

目标是先回答“已有深度时，手机能否实时做双眼偏移和补洞”。
使用当前 WebGL2 渲染器，真实 1080p 切片先在手机完整加载为 Blob，
输入持续移动的合成深度（96×54），关闭模型、运动传播和 Debug。
这项测试不验证 NPU、深度质量或完整 SBS 转换；不包含真实 NPU 取帧/搬运成本。

每眼 640、1280、1920 三档的三个片段各做 20 秒筛选，均达到源帧率
90% 的实验门槛。随后在每眼 1920×1080、Full-SBS 3840×1080 下，
三个片段各运行 60 秒，并逐帧 `gl.finish()` 等待 GPU 完成。
[带代码哈希的匿名数据](android-compositor-1080-sync-60s.json)。

| 片段 | 片源 fps | 合成 fps | 同步墙钟平均 ms | 同步墙钟 P95 ms | 解码丢帧 |
|---|---:|---:|---:|---:|---:|
| 1 | 23.976 | 23.70 | 2.70 | 7.90 | 0 |
| 2 | 23.976 | 23.77 | 2.63 | 7.70 | 0 |
| 3 | 25 | 24.86 | 2.57 | 7.30 | 0 |

计时后像素检查确认非黑画面、相对纯平面合成存在深度像素作用，
GL error 和隐藏页面帧均为零。每段视频循环，少量回调遗漏仍被记录。
回调间隔 P95 约 66–67 ms，因此平均吞吐通过不等同完美呈现节奏；
未测试眼镜物理显示。GPU timer 不可用，上表是包含提交和等待的 CPU
墙钟时间，不能标成 GPU 内核时间。短测中观察到电池 34.2°C、充电状态，
没有完整温度曲线或热稳定性结论。

证据支持默认视差、合成测试深度下的独立合成吞吐可行；下一项仍是
NPU 深度推理与取帧/回传延迟，再测两条链路并发。
